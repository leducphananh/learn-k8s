Cẩm Nang Toàn Diện Kubernetes

Khám phá bản đồ kiến trúc cụm, hệ thống phân cấp đối tượng từ Pod tới Ingress, giải phẫu manifest YAML và bảng tra cứu câu lệnh `kubectl` thực tế.

01. Nền Tảng Cốt Lõi

Kiến Trúc Cụm (Cluster Architecture)

Mô hình phân tán gồm Control Plane (Bộ não điều hành) và Worker Nodes (Nơi thực thi ứng dụng).

🧠

Control Plane (Master Node)

Kiểm soát trạng thái, nhận chỉ thị và phân bổ tài nguyên

kube-apiserver REST API Gateway

Cửa ngõ trung tâm tiếp nhận và xác thực mọi yêu cầu từ `kubectl`, UI hay các thành phần khác.

etcd Key-Value Store

Cơ sở dữ liệu phân tán lưu trữ toàn bộ trạng thái mong muốn (Desired State) của cả cluster.

kube-scheduler Bộ lập lịch

Theo dõi Pod mới tạo chưa có Node và tính toán để gán Pod xuống Worker Node tối ưu nhất.

kube-controller-manager Vòng lặp điều khiển

Liên tục so sánh trạng thái thực tế với trạng thái mong muốn và tự động kích hoạt sửa chữa (Self-healing).

⚡

Worker Nodes (Các Máy Thực Thi)

Môi trường hạ tầng chạy trực tiếp các Pod ứng dụng

kubelet Đặc vụ Node

Tiến trình chạy trên từng Node, nhận chỉ thị PodSpec từ API Server và đảm bảo containers khởi chạy khỏe mạnh.

kube-proxy Mạng & Routing

Cấu hình các luật mạng (iptables/IPVS) để các Pod và Service có thể kết nối thông suốt với nhau.

Container Runtime containerd / CRI-O

Phần mềm chịu trách nhiệm kéo image, khởi chạy và quản lý vòng đời container thực tế.

Pods & Storage Đơn vị triển khai

Nơi chứa 1 hoặc nhiều container cùng chia sẻ tài nguyên mạng (localhost), dung lượng và vòng đời.

kube-apiserver

Nhấp vào từng thành phần ở trên để xem chi tiết

API Server là trái tim của hệ thống Kubernetes. Tất cả giao tiếp giữa các thành phần bên trong (kubelet, scheduler, controller) và bên ngoài (kubectl) đều bắt buộc đi qua đây. API Server không lưu dữ liệu mà chỉ làm việc trực tiếp với etcd.

02. Mô Hình Đối Tượng

Hệ Thống Phân Cấp Tài Nguyên K8s

Cách Kubernetes tổ chức ứng dụng từ tầng mạng ngoài cùng xuống đến từng container.

🌐
Ingress / Gateway
Định tuyến HTTP/HTTPS domain bên ngoài
➔
🔀
Service (ClusterIP)
Load Balancer nội bộ & Địa chỉ IP tĩnh
➔
🚀
Deployment
Quản lý phiên bản, Rolling Update & Rollback
➔
🔄
ReplicaSet
Đảm bảo số lượng Pod luôn đúng mong muốn
➔
📦
Pod (Containers)
Chạy Node.js, Nginx, PostgreSQL...
Tại sao không tạo Pod trực tiếp?

Pod đơn lẻ không có cơ chế tự phục hồi (Self-healing). Khi Pod bị lỗi hoặc Node chết, Pod sẽ biến mất mãi mãi. Sử dụng Deployment sẽ giúp K8s tự động tạo lại Pod mới thay thế.

Service kết nối với Pod bằng cách nào?

Service sử dụng Label Selector (ví dụ `app: nginx`). Bất kỳ Pod nào có nhãn này sẽ tự động được Service thêm vào danh sách nhận traffic (Endpoints) mà không cần quan tâm IP của Pod bị đổi.

Cấu hình & Bí mật (Config & Secrets)

Dùng ConfigMap cho các biến môi trường cấu hình thông thường và Secret cho mật khẩu, token, SSL key để tách biệt hoàn toàn mã nguồn khỏi cấu hình hạ tầng.

03. Cú Pháp Manifest

Giải Phẫu Tương Tác YAML Manifest

Di chuột hoặc nhấp vào các dòng code bên trái để xem giải thích chi tiết ý nghĩa kỹ thuật bên phải.

🔍 Chọn một dòng để khám phá

Mọi tài nguyên trong Kubernetes đều tuân theo cấu trúc 4 trường gốc thiết yếu: apiVersion, kind, metadata và spec.

💡 Mẹo chuyên gia: Luôn dùng kubectl apply -f <file>.yaml để áp dụng cấu hình dạng Declarative (Khai báo trạng thái mong muốn).

Trung Tâm Lệnh Kubectl Thường Dùng

05. Gỡ Lỗi Nhanh

Xử Lý Các Trạng Thái Lỗi Của Pod

Hướng dẫn từng bước khi Pod không ở trạng thái Running.

💥 CrashLoopBackOff

Ứng dụng bên trong container khởi động nhưng bị crash và thoát ra liên tục (mã lỗi khác 0).

1. Xem log lỗi trước đó: kubectl logs <pod-name> --previous 2. Kiểm tra lệnh chạy: kubectl describe pod <pod-name>
⚠️ ImagePullBackOff / ErrImagePull

Kubernetes không thể tải Docker image từ container registry về máy worker node.

1. Kiểm tra lại tên image và tag: kubectl describe pod <pod-name> 2. Nếu là image private, kiểm tra cấu hình: imagePullSecrets
⏳ Pending

Pod chưa được gán vào Node nào do không đủ CPU/RAM hoặc Node bị dính Taints.

Xem phần Events ở cuối cùng: kubectl describe pod <pod-name> (Sẽ thấy thông báo 0/1 nodes are available...)
🛑 OOMKilled (Exit Code 137)

Ứng dụng dùng quá mức giới hạn RAM (Memory Limit) được cấp và bị hệ điều hành hủy.

Nâng ngưỡng tài nguyên trong YAML: resources.limits.memory: "512Mi"

⚡ Mẹo Thực Hành Với OrbStack Trên macOS

Bạn không cần dùng Minikube hay Kind. Cụm K8s của OrbStack đã được tối ưu sẵn cho chip Apple Silicon, tự động định tuyến mạng trực tiếp vào Pod IP (ví dụ curl http://192.168.194.x) mà không cần qua bước NodePort hay Port-forward rườm rà.
